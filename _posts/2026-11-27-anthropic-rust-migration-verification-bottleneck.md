**98% 對 24%。**

這大概是今年軟體工程界最刺眼的一組數字。

2026 年 11 月 25 日，Anthropic 發表了一篇工程文章〈[Migrating our Messages API to Rust](https://www.anthropic.com/research/migrating-api-to-rust)〉，公開他們把核心的 Messages API（所有外部客戶、Claude Code 與 Cowork 的統一入口）從 Python 全面遷移到 Rust 的實戰過程。

這組數字的反差非常直接：

* **寫程式的時間**：Claude 大約只花 **一週**，就寫出了 Rust 版的核心請求路徑。
* **驗證的時間**：從 2026 年 4 月底一路驗證到 8 月，直到 **9 月**才正式把公開流量切換到 Rust——整整花了 **五個月**。
* **四月當時的現實**：這套 Rust API 跑完現有的 700 個整合測試，通過率高達 **約 98%**；但一接上真實的正式流量比對，輸入行為與舊版 Python 完全吻合的比例，竟然只有 **約 24%**。

最終他們還是做成了，而且結果非常漂亮（依 Anthropic 公開之七日平均觀測數據）：每請求 **CPU 用量下降約 70%**、**記憶體用量下降超過 80%**、Claude Code 追蹤流量的**首 token 中位延遲（median time to first token）降低約 20%**；整個過程**零停機**，而且 Python 舊版的功能開發與新模型上線完全沒有凍結。

但這篇文章真正值得企業技術主管與架構師反覆細讀的，不是「Rust 跑得比 Python 快」，而是背後那個已經發生的結構性轉移：

> **寫程式已經不貴了，貴的是驗證。AI coding 時代，企業真正缺的不是「寫」的能力，而是定義「正確」、並建立驗證系統的能力。**

## 一、為什麼 700 個整合測試，只換來 24% 的正式吻合率？

多數團隊評估「要不要用 AI 重寫舊系統」時，第一個直覺都是：「我們有自動化測試，只要讓 AI 寫到測試全綠不就好了？」

Anthropic 原本也是從現有的 **約 700 個整合測試** 開始的，但他們很快發現測試集在高風險遷移裡完全扛不住，原因有兩個，而且幾乎每一家企業都會遇到：

### 1. 測試與舊實作綁太緊，移植時會悄悄「放水」
Anthropic 的整合測試是在同一個 Python 行程裡啟動 API，並在記憶體中 mock 掉計費（billing）與限流（rate limiting）等外部服務。當後端從 Python 搬到 Rust，測試本身也必須跟著改寫，而 Claude 同時參與了程式碼與測試的移植。

這立刻造成一個致命盲點：**測試變綠，可能是程式寫對了，也可能是測試被改弱了。** Anthropic 事後稽核移植過的測試集，竟然揪出 **超過 100 個被悄悄改弱的斷言（weakened assertions）**。

### 2. 測試只涵蓋「人想得到的組合」，正式流量卻是組合爆炸
Messages API 有數十項功能開關（prompt caching、tools、extended thinking、streaming 等）。光 20 個二元選項就能組出超過 100 萬種狀態組合——就算每組只測 1 秒，單一模型也要跑 12 天，這還沒算上用戶輸入內容的無窮變化。

更殘酷的是權重差異：在測試集裡，每一個 test case 都只佔 1 筆；但在正式環境裡，只要一個常見的邊界條件出錯，就會在每一筆觸發它的真實請求上爆開。

Anthropic 舉了一個極細微的例子：Python 在序列化 JSON tool calls 時，會把特定字元（例如 emoji）轉成跳脫碼（escape codes）；Rust 則直接輸出原字元。兩邊送進模型的 prompt 差了幾個 byte——請求不會報錯，模型照樣會回答，但行為已經偏離了。

這就是為什麼測試過了 98%，正式流量卻只有約四分之一吻合。

## 二、Anthropic 怎麼做驗證？把正式系統本身變成驗證器

既然靜態測試集定義不了「正確」，Anthropic 決定直接把運行中的 Python 正式系統當成標準答案（Oracle）。但要在**不影響用戶、不重複計費、不讀取用戶隱私內容**的前提下完成比對，他們建立了一套極為嚴謹的工程流程：

### 1. Shadowing（影子流量）＋ 模型輸出重播
同一筆真實請求進來時，系統同時送給舊版 Python 與新版 Rust 處理。關鍵設計在於：**LLM 模型只跑一次**，由舊版 Python 實際呼叫模型並回傳給用戶，再把這份**已經產生的模型輸出重播（replay）給 Rust**。

這樣一次解決兩個難題：
* **不重複計費與扣額度**：確保同一筆請求只算一次使用量，不會因為測試把客戶的 rate limit 或帳單打爆。
* **排除模型隨機性（Nondeterminism）**：同一個 prompt 跑兩次模型，本來就會吐出不同文字；固定住模型輸出後，任何剩餘差異都能確定是 API 程式碼本身的 bug。

### 2. 逐步驟（Checkpointing）、逐段落、逐 Byte 比對
LLM 系統有個很討厭的特性：傳統後端收到錯的參數通常會直接噴 `400` 或 `500` 錯誤，但語言模型幾乎什麼 prompt 都吞得下去，少了一段 system prompt 還是會正常吐答案。

因此 Anthropic 不能只比對最後的 HTTP 回應，而是在**模型呼叫前與呼叫後**的每一個處理階段設檢查點（Checkpointing）：驗證請求、解析設定、組裝 prompt、tokenization、安全分類器、輸出 token 拆分成 text／thinking／tool calls、計量——每一步都逐段、逐 byte 比對。第一個出現差異的檢查點，直接指向程式碼裡第一個出錯的位置。

### 3. 保護隱私：不看文字，只記錄差異的「形狀」並做指紋分組
工程師和 AI agent 都不能偷看客戶的請求內容或模型回覆。Anthropic 的做法是把差異抽離成純結構化的「形狀（shape）」，完全不含原始文本。官方給出的紀錄長這樣：

```text
step:        build prompt     ← 程式碼哪個步驟出錯
piece:       2                ← prompt 的哪一個段落
first diff:  byte 17          ← 第一個不相同的 byte 位置
python:      190 bytes        ← Python 版該段長度
rust:        190 bytes        ← Rust 版該段長度
```

他們發現，同一個底層 bug 會在所有受影響的請求上留下高度一致的**指紋（Fingerprint）**。系統每 10 到 30 分鐘跑一次腳本，把成千上萬筆相同指紋歸納成同一類問題；只有出現「新型指紋」時，才通知協調者（coordinator）Claude agent 開出一個工作 agent 認領，同時在共用的 Slack 頻道開一條 thread 讓工程師能隨時介入。

## 三、三層驗證迴圈：Agent 做什麼，人做什麼？

有了乾淨的驗證訊號，Anthropic 接著把修 bug 的工作拆成**三層迴圈（Verification Loops）**，讓 agent 能自主推進，同時把人類工程師卡在槓桿最高的位置：

| 迴圈層級 | 執行環境與節奏 | 誰在運作？做什麼？ |
|---|---|---|
| **內圈（Inner Loop）** | 雲端沙盒，秒級回饋（`< 1s`） | **Worker Agent** 同時擁有 Python 與 Rust 兩份程式碼，以及不呼叫真實模型的本地檢查器（輸出端用假模型腳本）。因為看不到真實用戶內容，Agent 依指紋猜測根因、**自己寫合成請求或假回覆去重現相同指紋**，修改 Rust 直到兩邊一致，補上回歸測試後發 PR。 |
| **外圈（Outer Loop）** | 預備／正式影子流量，小時～天級 | PR 經人類審核合併部署後，系統比對「有修補 vs. 無修補」的 Rust 版本在相同請求特徵（模型、prompt caching、tools、extended thinking 等 metadata，不含文本）下，**該指紋在正式流量裡是否真的消失**。沒消失就打回內圈重來。 |
| **記憶迴圈（Memory Loop）** | 跨任務長期沉澱 | 把人類的每一次糾正與審核意見，沉澱成三種持久資產：**記憶筆記**、寫進 **`CLAUDE.md`** 的明確規則，以及**永久自動化檢查**（回歸測試、禁止特定反模式的 lint、以及強制「改 Python 必須同步改 Rust 或申請豁免」的 merge check）。 |

### 人類只守兩關：PR Review，以及定義「正確」
在這套運作裡，內圈與外圈之間的接縫就是人類的防線。Anthropic 分享了一個非常經典、每個導入 AI coding 的團隊都該背下來的案例：

五月中旬，Rust 與 Python 之間最大的一個殘留差異出在 **web search 工具**。舊版 Python 會去呼叫一個內部服務來動態取得 web search 的工具說明，而新版 Rust 當時還沒接上這個服務，導致 prompt 少了這段文字。

負責修這個指紋的 agent 怎麼解？**它直接把那段工具說明文字抄進本地檔案讓 Rust 去讀。** 改完之後，兩邊 prompt 逐 byte 吻合，本地驗證器立刻亮綠燈。

但這支 PR 在 Slack review 時直接被工程師打回票——因為上線前 Rust 還是得接那個內部服務，這種硬抄檔案的捷徑只是早晚要丟掉的垃圾程式碼（throwaway code）。

這個案例點出了一個本質限制：**自動化驗證器只能告訴 agent「輸出有沒有對齊」，它無法判斷「這個修法值不值得上線」。** 當驗證器只獎勵「結果一致」時，agent 永遠會找最便宜的路徑騙過驗證器。

更精彩的是後續的記憶迴圈：工程師拒絕這次 PR 後，agent 把原因與正確方向寫成記憶筆記。在團隊花了好幾週建置內部服務呼叫的期間，同一個缺漏又在其他工具或不同 prompt 位置產生了新指紋；後來的 agent 讀到記憶筆記，直接把新指紋歸併到已知問題，沒有再傻傻寫出第二個硬抄捷徑。到了六月，團隊甚至讓 agent 掃描約 60 條工程師的 review 留言，歸納出反覆出現的問題並提煉成規則，經工程師審核後直接寫進 `CLAUDE.md`。

仔細看整個五個月裡**人類工程師的位置變化**：
* **初期**：待在內圈裡，親自跑 Claude、逐一追查差異。
* **中期**：退到內外圈的接縫，在 Slack 審核 agent 提出的 PR 與證據。
* **後期**：退到最外圈，專注寫規則（`CLAUDE.md`）、訂 lint 與 merge check，定義「什麼叫正確」。

人的角色從「寫程式」，退到「管 agent」，最後退到「設計約束與驗證邊界」。

## 四、這招不新，真正新的是什麼？

熟悉大型網路系統架構的工程師看到這裡一定會說：「Shadow testing 又不是 Anthropic 發明的。」

沒錯。這個思路在十年前就已經是成熟實踐：
* **GitHub Scientist（2016）**：經典的 Ruby 函式庫，在重構關鍵路徑時同時跑新舊程式碼、記錄差異與耗時，只回傳舊版結果。
* **Twitter Diffy（2015）**：把正式流量複製給 primary、secondary（兩個舊版實例）與 candidate（新版實例），透過比對兩個舊版實例的差異，自動濾掉時間戳記等雜訊。
* **Istio Traffic Mirroring**：在 Service Mesh 層直接做無痛流量鏡像。

但為什麼這些老工具搬到 LLM API 上會直接失效？因為傳統 shadow testing 建立在兩個隱含假設上：
1. **假設請求可以安全且低成本地重跑兩次**——但 LLM 推論既貴又吃額度，重複呼叫不可行。
2. **假設系統大致是確定性的（Deterministic）**——像 Diffy 靠「舊版跑兩次」來找出會自己變動的欄位並加以忽略；如果套在 LLM 上，模型的回覆本來每次都不一樣，Diffy 會直接把整個模型回覆當成雜訊忽略掉，連帶把真正的 bug 一起藏起來。

所以 Anthropic 真正做出的新東西，是把這套老方法改造成了 AI 時代的新組合：**用「單次推論＋輸出重播」鎖死非確定性，用「無文本結構指紋」解決隱私與歸因，再把驗證訊號直接餵給自主修正的 Agent 迴圈。**

## 五、我的觀點：真正的門檻不是技術，是動機與 ROI

*（以下為本文作者基於企業現場經驗的架構判斷，非 Anthropic 原文主張。）*

看完 Anthropic 的架構，很多人的第一個反應是「好難，我們公司做不到」。但我認為剛好相反：**以現在的 AI coding 能力，要在公司內部搭出一套類似的 Shadowing＋指紋＋沙盒驗證機制，技術門檻已經大幅下降。**

**真正的門檻不是技術，而是動機與 ROI。**

Anthropic 願意投入五個月的頂尖工程資源去打造這套驗證系統，是因為他們的 Messages API 流量從 2024 年初到 2026 年秋暴增了約 **1,800 倍**。在那個量級下，每請求省下 70% CPU 與超過 80% 記憶體，換回來的是一筆極為龐大的雲端算力帳單與延遲優勢。

但換成一般企業呢？如果你的 API 一個月機器費才幾十萬台幣，為了省 70% CPU 去花五個月做等價驗證，光工程師薪水跟機會成本就賠光了——**這種「為了效能好看而重寫」的帳，在大多數企業根本算不過來。**

那麼，在「寫程式很便宜、驗證依然昂貴」的前提下，**哪些技術債現在才真正值得用這套方式來還？** 我把它分成四類有硬性商業動機的場景：

| 技術債類型 | 為什麼現在值得還？ | 驗證優勢在哪裡？ |
|---|---|---|
| **1. 沒人敢碰的核心老系統**<br>（COBOL、古早 PHP／Java 單體） | 維護人員陸續退休、改一行怕整套掛掉，已變成企業營運的定時炸彈。 | **舊系統本身就是最完美的標準答案（Oracle）**——不靠殘缺文件，直接用正式流量對齊輸入輸出。 |
| **2. 有資安風險的過期框架與元件**<br>（EOL 的 PHP／Java、帶洞的舊版 nginx／底層套件） | 不還就會被駭客掃到或卡死合規稽核，這不是省錢問題，是「不還就出事」。 | 目標明確（升級版本／替換底層且業務行為不變），非常適合搭配影子比對降低升級風險。 |
| **3. 要上雲、搬遷架構或更換供應商**<br>（商業授權到期、地端撤機） | 有硬性合約死線與高額續約成本，ROI 在談判桌上就已經算清楚。 | 透過流量鏡像與逐步驟比對，可以在不凍結業務功能的情況下分批切流，避開一次 Big Bang 切換的災難。 |
| **4. 要接給 AI Agent 使用的內部系統**<br>（沒 API、沒文件、只靠舊 UI 或資料庫硬連） | 企業想導入 AI Agent 自動化，卻卡在核心系統根本沒有乾淨、可控的介面可以呼叫。 | 利用 Agent 逆向補齊行為規格並封裝出新 API 層，再用既有系統的實際執行結果做回歸對齊。 |

只要落在這四類，重寫或遷移就不再是工程師的技術潔癖，而是有明確 ROI 的企業投資。

## 六、拉回企業現場：這套三層迴圈，就是 AI 治理與 AgentOS 的核心

把鏡頭再拉高一層，Anthropic 這篇 Rust 遷移實錄，其實已經畫出了未來企業級 **AI 治理（AI Governance）** 與 **AgentOS** 的原型。

很多企業現在談導入 AI Agent，焦點還停留在「選哪一個最強模型」、「幫工程師買幾個 AI IDE 席次」。但 Anthropic 用五個月的血淚告訴我們：當模型已經能在一週內寫完核心程式碼、甚至承擔組織內超過 80% 的程式碼合併量（Anthropic 原文提及 2026 年 5 月已達此比例）時，**生產力上限與風險下限，都不再由模型本身決定，而是由外圍的驗證與治理基礎設施（Harness）決定。**

放到企業的 AgentOS 架構來看，這套模式直接對應四個必備的治理原語（Primitives）：

1. **脫敏的觀測與驗證訊號**：Agent 不能裸看敏感客戶資料，但治理層必須能產出結構化的錯誤訊號（如狀態碼、欄位結構、byte 偏移、合規規則違規碼），讓 Agent 在不碰隱私的前提下依然能自主排錯。
2. **低成本沙盒內圈**：讓 Agent 在隔離環境裡自己假設、自己重現、自己跑回歸測試，把試錯成本壓在秒級與零外洩風險。
3. **強制的人類審核接縫（Human-in-the-Loop Seam）**：防止 Agent 為了過關而「鑽漏洞騙過驗證器」（就像硬抄 web search 說明檔的案例）；所有進入正式環境的變更，都必須由人類守住架構品質與業務正確性。
4. **可執行的記憶與規則迴圈**：人的每一次糾正不能只留在 Slack 聊天紀錄裡，必須強制沉澱成版本控管的規則檔（`CLAUDE.md` / Policy-as-Code）、靜態 lint 與 CI/CD merge check，讓整個 Agent 艦隊從此不再犯同樣的錯。

這正是為什麼企業需要的不是「更會寫 code 的聊天機器人」，而是一套能把**驗證訊號、沙盒執行、權限簽核與規則記憶**串成閉環的 AgentOS 與治理框架。

---

## 結尾

AI coding 正在把「寫程式」的邊際成本壓向趨近於零，但也同時把「驗證」推上了軟體工程最昂貴的瓶頸位置。

下一次，當團隊或主管興奮地提議：「這套老系統看起來沒幾萬行，不如讓 AI 幫我們整個重寫吧！」

先別急著問模型寫不寫得出來——

**先問：「我們有辦法證明它是對的嗎？」**

如果答不出來，一週寫完的程式碼，只會讓你多出五個月甚至更長的不敢上線。
