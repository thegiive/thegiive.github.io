## 引言：AI Coding 的熱潮與我的觀察

這半年來，AI coding 工具大行其道，從 Cursor 到 Claude Code，從 GitHub Copilot 到各種 Agent 框架，社群討論熱度一直沒停過。

但老實說，我想從一個實際在用這些工具的工程師角度，談談這段時間的真實變化。不是那種「AI 會取代工程師」的焦慮販賣，也不是「AI 讓生產力飆升 10 倍」的過度美化。

就是一個在 production 環境裡用 AI Coding 快1 ~3 年的人(我在 2023 年就用ChatGPT 在 Copy Paste AI Coding) ，講講需求轉化和工具進化這兩件事的真實體驗。

## 一個反直覺的觀察：Coding 能力早就夠了

這一年來 AI Coding 進步的範疇很多，但如果你問我真正的瓶頸在哪裡，我其實覺得

**其實從 Sonnet 3.5 之後，Coding 能力就已經很夠用了。**

老實說，GPT-4 時代就已經很棒了。你給它一個清楚的需求，它能寫出 85% 以上可用的程式碼。剩下的 15% 需要人工調整，但這個比例從 2024 年初到現在，並沒有戲劇性的變化。

那這一年工具到底在進步什麼？

**答案是：獲取足夠的上下文。**

想想看，為什麼 Cursor 比純 ChatGPT 好用？因為它能讀你的 codebase。為什麼 Claude Code 比 Cursor 在某些場景更強？因為它有 Agent 能力，可以主動去搜尋、讀取、理解你專案的結構。

AI 的 coding 能力早就到位了，但它一直受限於「不知道你的專案背景知識長什麼樣」。

這就是為什麼：
- **Context window 從 8K 擴展到 200K** 是大事
- **MCP（Model Context Protocol）** 這類工具開始被重視
- **RAG 和 codebase indexing** 變成標配功能

所有的進化方向(Cursor, Claude Code)，都在解決同一個問題：**讓 AI 知道更多你的上下文**。

而「上下文」這件事，最難的部分不是技術，是需求。

## 需求轉化的挑戰：PRD 的提取困境

理解了上下文是瓶頸之後，我們來看最難獲取的上下文：**客戶需求**。

我們在實務中發現一個很大的難題：**如何把客戶需求轉化成清晰的 PRD**。

這件事在 AI Coding 之前就很難了，AI Coding 之後還是一樣難。舉個實際的例子。我們有一個重要的客戶，即使是跟已經合作三年的 PM 溝通，仍然會因為對方使用了很多行業黑話和複雜的業務邏輯而產生誤解。

這種需求提取本身就是兩個「腦袋」對接的過程。

客戶腦袋裡想的是業務場景，PM 腦袋裡想的是系統功能。如果雙方不在同一層次理解，很容易產生誤會。我們之前統計過，第一次訪談拿到的需求，準確率大概只有 60-80%。剩下的 20-40% 要靠後續的迭代才能補齊。

當然，你可以說客戶應該先把 PRD 寫好。

但想想看，TDD、BDD 這些理念談了這麼多年，需求文件一直是個難題。在快速變動的業務中，實際上，這本質上就是無法被完美解決的。

**AI 能幫忙寫 PRD 嗎？能。但它沒辦法幫你「懂」客戶在想什麼。**

這是兩件事。

## 團隊內的調整與工具進步

接下來談談團隊內的變化。

AI coding 的導入確實讓生產力提升了一些。但這個「一些」要講清楚是什麼意思：

- **程式碼產出速度**：提升明顯，大概 40% 左右
- **Debug 時間**：反而沒有明顯減少，有時候還更長（因為 AI 產出的 code 你不熟悉）
- **驗收時間**：增加了，因為產出量變大，驗收工作量也跟著變大

所以核心挑戰仍在於**驗證**和**需求的不確定性**。

對我來說，這半年更多是工具變得更方便，讓入門門檻降低。但 AI coding 的核心能力其實早就足夠了——2024 年初的 GPT-4 已經能做大部分的事情，現在只是變得更便利、更穩定、更少出錯。

## 實務場景的補充

在實務中，我們針對不同行業的客戶需求，搭建系統、網頁或 App。

老實說，這些其實大多是一些 CRUD 加上基本業務流程，不算特別困難。我們團隊用 [ATPM 框架](/atpm-a-real-production-vibe-coding-process/) 搭配 AI Coding，處理這類需求已經很順手了。

而在數據分析和機器學習建模上，有像 Claude 4.0（現在是 Claude 4.5）以上的工具，基本上都能很好地解決問題。我之前寫過[三個月 63 萬行](/claude-code-630k-lines-three-months-reflection/)的經驗，裡面 90% 都是數據分析相關的一次性程式。

但這些「能解決的問題」，都有一個共同前提：**你要先知道問題是什麼**。

## 工具進化的觀察：從 Copilot 到 Agent

理解了「上下文是瓶頸」這個前提，工具進化的方向就很清楚：
1. **從補全到對話**：Copilot 是「你打字，它補全」；Claude Code 是「你描述問題，它解決」。你不再需要知道語法，但要會描述問題。
2. **從單點到流程**：以前只能處理單一檔案，現在 Agent 可以跨檔案、跨系統。Claude Code 的 Task 能同時派多個 subagent 處理不同事情。
3. **從工具到夥伴**：用久了之後，它就像一個有點呆板但非常可靠的同事——需要的時候一定在。

## 沒有改變的事情

說完進步的部分，也要講講沒有改變的事情：

### 1. 需求定義還是人的工作

AI 可以幫你寫 PRD，但它沒辦法幫你決定「應該做什麼」。這個決策權還是在人手上。

### 2. 驗收還是需要人

我在 ATPM 框架裡一直強調 [QA 的重要性](/atpm-qa-ru-he-yan-shou-ai-coding-de-cheng-shi/)，因為 AI 產出的東西再多，沒有人驗收就等於零。

這半年下來，我花在驗收上的時間比例反而變高了（從 50% 變成 70%）。因為 AI 產出速度快，驗收如果跟不上，品質就會出問題。

### 3. 複雜業務邏輯還是很難

那種需要深入理解業務場景、需要跟多個部門協調、需要考慮歷史包袱的專案，AI 幫不了太多。

它可以幫你寫程式碼，但它沒辦法幫你理解「為什麼這個業務流程要這樣設計」。

## 對 Vibe Coding 社群的觀察

坦白說，我現在大大小小的 Vibe Coding 討論聽下來，大家講那麼多東西，但**很少人著重於如何把 QA 這件事情做好**。

這讓我很疑惑。

大家都在討論怎麼讓 AI 產出更快、更多、更好。但很少人討論：產出這麼多東西之後，誰來驗收？怎麼驗收？驗收標準是什麼？

如果你只會讓 AI 生成程式碼，但不會定義規格、不會驗收品質，那你只是在「玩」AI，不是在「用」AI。

我自己觀察，可以先從三件事開始補齊：

1. **把需求寫成「可驗收條件」**
   不用懂語法，但一定要能回答：什麼情況算做對？什麼情況算失敗？

2. **先用 AI / Low-code 做「需求展開」**
   哪怕是 Excel、Notebook、或 AI 產出的 Prototype，重點不是漂亮，而是讓需求被「具體化」。你會更理解，未來要用的人也更理解。

3. **Start small, small is way better than null**
   從小的開始，比什麼都沒有好太多。這某種程度上，是最快可以補上的關鍵價值。

## 結語：現實的期望與未來展望

總結這半年的觀察：

**AI coding 的進步更多是讓更多人能參與，但需求轉化的挑戰依然存在。**

工具變好用了，門檻降低了，但核心難題沒有被解決。那些「人」的問題——需求理解、業務判斷、品質驗收——還是需要人來處理。

我的建議是：

1. **擁抱工具進步**：新工具真的比舊工具好用，沒必要固守舊的做法
2. **保持現實期望**：AI 不會讓你變成 10x 工程師，但可能讓你變成 1.4x 工程師
3. **投資在驗收能力**：當產出變得廉價，驗收能力就變得稀缺
4. **持續學習需求定義**：這是 AI 最難取代的能力

希望這些觀察能給你一些啟發。

我們在擁抱 AI 工具的同時，也要對現實保持清晰的認知。畢竟，工具再強，最後還是要解決人的問題。
